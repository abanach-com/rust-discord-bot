# Lua author handbook

This handbook describes Lua API **1** as implemented by ZuckerBot at source snapshot [`10a2ba1`](https://github.com/abanach-com/rust-discord-bot/tree/10a2ba1780a2becd6d7ba2bfc5c4f7a2fecc9882). The public entry point remains [Lua module API](../LUA_API.md). Source links in these chapters are relative to this repository so the contract can be checked alongside the code.

Lua decides which actions to request. Rust loads modules, builds contexts, validates their output, enforces execution rules, owns storage, and calls Discord. A declaration in a Rust type is not by itself a usable Lua feature: the [support matrix](support-matrix.md) distinguishes registration, dispatch, execution, and restricted service access.

## Runnable examples

[examples/lua](../../examples/lua/README.md) contains three independent packages and a separate installer:

- `hello`: a simple command with a string option and an optional user ID.
- `nested-router`: subcommands and a subcommand group with the actual nested context shape.
- `event-audit`: event handling with explicit configuration and bounded audit metadata.

They are documentation examples, outside the production `scripts/install.xml` selection. Read the installation instructions before running a bot against Discord: command registration changes the selected application's command set.

## Reading conventions

- **Required** means there is no deserialization default; supply the field even when an example value appears obvious.
- An omitted optional field becomes Rust `None`; inside Lua, absence is normally `nil`.
- Tables marked **array** use consecutive integer keys starting at `1`.
- Bounds described as characters use Rust Unicode scalar values unless explicitly marked **bytes**. Lua `#text` counts bytes.
- Discord IDs are decimal **strings**. Treat them as opaque identifiers.
- A successful Lua invocation yields validated action requests. It does not prove that Discord accepted those actions.
- Service responses are generated by Rust. They are not return values that a Lua script can capture.

## Sources and documentation scope

The primary contract is [model.rs](../../src/lua/model.rs), [engine.rs](../../src/lua/engine.rs), the service operation models in [src/lua](../../src/lua), and the Discord [handler](../../src/discord/handler.rs), [command builder](../../src/discord/commands.rs), and [executor](../../src/discord/executor.rs). Existing operator guides for [moderation cases](../MODERATION_CASES.md), [tickets](../TICKETS.md) and [scheduler](../SCHEDULER.md) provide deployment context; this handbook documents the Lua-facing field contract.

This documentation describes the source snapshot. It does not assert that the full Rust test suite, production Discord delivery, or every shipped Lua command has passed verification. See [testing](testing.md) for the difference between syntax checks, engine tests, service tests and live integration checks.
