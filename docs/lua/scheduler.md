# 8. Scheduler

[Handbook index](README.md) · Previous: [Progression](progression.md) · Next: [Tickets](tickets.md)

**Access:** only the runtime module ID `scheduler` may use this action. It requires an interactive command, a guild and an actor. An arbitrary module or an event handler cannot create scheduler jobs. The operation model is [src/lua/scheduler.rs](../../src/lua/scheduler.rs); command execution is in [src/discord/scheduler.rs](../../src/discord/scheduler.rs), and the worker and delivery path are in [src/scheduler/mod.rs](../../src/scheduler/mod.rs). See also the [operator guide](../SCHEDULER.md).

## `create`

```lua
-- Action fragment for the existing trusted scheduler module.
{ type = "scheduler", operation = {
    type = "create",
    when = "15m",
    content = "Review the deployment status.",
    mention_creator = false,
    max_jobs = 20,
    minimum_delay_seconds = 10,
    maximum_delay_seconds = 2592000
} }
```

| Field | Type | Required/default | Constraint/meaning |
| --- | --- | --- | --- |
| `when` | String | Required | Trimmed length 1–128; accepted syntax below |
| `content` | String | Required | Trimmed length 1–1,800 |
| `channel_id` | Snowflake string or absent | Absent | Default current channel; explicit destination is a staff operation |
| `repeat` | String or absent | Absent | Trimmed length 1–64; duration syntax; staff operation |
| `repeat_count` | Unsigned 32-bit integer or absent | Absent | 2–10,000; requires `repeat`; includes the first delivery |
| `mention_creator` | Boolean | `false` | Controlled creator mention at delivery |
| `max_jobs` | Unsigned 16-bit integer | Required | 1–500; policy limit |
| `minimum_delay_seconds` | Unsigned 32-bit integer | Required | 10–3,600 |
| `maximum_delay_seconds` | Unsigned 64-bit integer | Required | At least minimum, at most 315,576,000 |

The three policy limits have no serde defaults. A fragment omitting them does not become a valid create operation. Put them in trusted module policy/configuration, not unrestricted user options.

At creation, the executor checks the destination guild and channel type. This check does not preflight the bot's eventual send permission: a job can be accepted and later fail when Discord rejects delivery. Job creation is rate-limited through the scheduler creation bucket.

## Time syntax

| Input | Interpretation |
| --- | --- |
| `15m` | Fifteen minutes from creation time |
| `1h30m` or `1h 30m` | Compound positive duration |
| `2d`, `1w` | Days or weeks |
| `in 15m`, `za 15m` | Supported duration prefixes |
| A bare integer string | Unix timestamp in seconds, **not** a number of seconds from now |
| `2027-01-15T18:00:00+01:00` | RFC 3339 absolute time with explicit offset |

Duration units are `s`, `m`, `h`, `d`, and `w`, with positive integer quantities. Units are case-insensitive. Use the lowercase `in ` or `za ` prefix; prefix stripping happens before duration normalization. The due time must satisfy the supplied minimum and maximum delay policy.

There is no cron parser, natural-language date parser, local-timezone guessing or Lua timer callback. Prefer an explicit RFC 3339 offset for absolute dates. A recurring interval uses duration syntax and must be between 60 and 31,557,600 seconds. Without `repeat_count`, a recurring job has no count-based end.

```lua
{ type = "scheduler", operation = {
    type = "create", when = "1h", ["repeat"] = "1d", repeat_count = 7,
    content = "Daily checklist", max_jobs = 20,
    minimum_delay_seconds = 10, maximum_delay_seconds = 2592000
} }
```

## `list`

| Field | Default | Constraint |
| --- | --- | --- |
| `scope` | `mine` | `mine` or `all` |
| `limit` | `10` | Unsigned 8-bit integer, 1–20 |

`mine` lists the actor's jobs in the guild. `all` requires `MANAGE_GUILD` or administrator. The resulting text is generated by Rust and is not a list Lua can iterate.

## `cancel`, `pause`, `resume`

Each operation requires `job_id`, a complete valid UUID string:

```lua
{ type = "scheduler", operation = {
    type = "pause", job_id = "00000000-0000-4000-8000-000000000001"
} }
```

The UUID above illustrates the format only; use an existing job ID returned by the service. Partial IDs and Discord snowflakes are not scheduler job identifiers. The executor checks the current guild and ownership; administering another user's job requires `MANAGE_GUILD` or administrator. Job state can additionally make an operation invalid.

## Permission summary

| Operation | Staff requirement |
| --- | --- |
| One-time create in current channel | Normal authorized caller, within policy and rate limits |
| Create with explicit `channel_id` | `MANAGE_GUILD` or administrator |
| Create recurring job or repeat count | `MANAGE_GUILD` or administrator |
| List own jobs | No additional staff permission |
| List all jobs | `MANAGE_GUILD` or administrator |
| Cancel/pause/resume own job | Ownership and state checks |
| Cancel/pause/resume another user's job | `MANAGE_GUILD` or administrator |

## Worker lifecycle and reliability

The worker runs in Rust, independently of the VM that created the job. The current implementation polls every five seconds and claims up to ten due jobs. Delivery concurrency defaults to four and can be changed with a positive `SCHEDULER_CONCURRENCY` environment value. Claims use a 60-second lease, renewed every 20 seconds; a delivery attempt has a 30-second timeout. The polling and lease timings are current implementation constants; concurrency is host environment configuration. None is a Lua operation field.

Failures retry up to five attempts with an exponential delay starting at five seconds and capped at 300 seconds. Exhausted jobs enter a failed state. A recurring job advances from its previous scheduled time; overdue advancement is constrained to a future time rather than delivering an immediate burst for every missed interval.

Durable storage and leases do not promise exactly-once Discord delivery. A crash after a successful HTTP delivery but before recording success can create an uncertain result. Avoid using scheduled messages as an irreversible accounting transaction.

PostgreSQL is necessary for persistence across process restarts. Without `DATABASE_URL`, in-memory jobs disappear when the bot stops. Inspect worker logs, current job status, channel permission changes and database connectivity when a job appears late or failed. Do not assume that a successful `create` response means that the later Discord send has succeeded.
